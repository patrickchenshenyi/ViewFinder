## 0. 本文的动机

在讨论「Photo-SLAM 的 3D 建模质量为什么不够高」时,得到的结论是:当前链路里**位姿和几何是从同一批 2D 观测里联合解出来的**,这带来一组结构性的质量问题(见 §1)。一个自然的设想是:**把位姿这一项从优化里拿掉,改成外部给定**,即用手机自带的 VIO(ARCore)提供米制位姿。

本文把该设想整理成可评估的设计:讲清原理(§2–§4)、ARCore 能提供什么(§5)、具体架构(§6)、预期收益(§7)、代价与风险(§8)、以及最小验证路径(§10)。

**本文不含任何实测数据。§7 的收益全部是「预期」,未被验证。**

## 1. 背景:当前链路的位姿从哪来

现状(`docs/plan.md` §3、`docs/gs_slam_deployment.md` §4):

```
IP Webcam(RTSP) → ffmpeg 抽帧 → ORB-SLAM3 单目
                                    ├─ 从 ORB 特征估位姿
                                    └─ 从 ORB 特征建稀疏地图   ← 两者共享同一批观测
                                 → Photo-SLAM Gaussian mapper(位姿 + 几何联合优化) → splat
```

这是**联合估计(joint estimation)**,已有几个已知病症:

| # | 病症 | 机制 |
|---|---|---|
| 1 | 几何「弯过去迁就位姿」 | 位姿和几何是同一批观测的自由度,误差可互相抵消;重投影/photometric loss 允许这种解 |
| 2 | 单目尺度不可观 | 整场景缩放 + 相机轨迹同步缩放产生逐像素相同的图像序列。这不是算法差,是**规范自由度**(gauge freedom) |
| 3 | 快速旋转丢跟踪 | 相机 30Hz,帧间运动大时 ORB 匹配断裂;且帧间无信息 |
| 4 | 延迟被 BA 占用 | 每帧都在重新解位姿 |

`docs/plan.md` §6 已把第 2、3 条列为已知风险,对策写的是「接受」+「降速/回环」;并把 IMU 列为**后期可选**(VINGS-Mono 方向)。
本提案的核心主张是:**IMU/VIO 是一阶杠杆,而不是后期可选**。

## 2. 前置知识 A:IMU 是什么

IMU = **I**nertial **M**easurement **U**nit,惯性测量单元。手机里是几颗 MEMS 芯片,核心是两支:

| | 测什么 | 单位 | 典型频率 | 短期精度 | 长期表现 |
|---|---|---|---|---|---|
| 陀螺仪 (gyroscope) | 自身角速度 | rad/s | 200–1000 Hz | **极好** | 缓慢漂移 |
| 加速度计 (accelerometer) | 比力(specific force);静止时读数即重力反作用 | m/s² | 200–1000 Hz | 好 | **积分后灾难性** |

**为什么不能只靠它(积分漂移的量化):**

- 陀螺仪:角速度积分得角度。零偏 0.01 °/s → 60 秒累 0.6°。短期几乎完美。
- 加速度计:加速度积分两次得位置,误差随 ½·b·t² 增长。零偏 0.01 m/s² → 10 秒错 0.5 m,100 秒错约 50 m。**完全无法用于定位。**

**为什么又不可替代——加速度计提供两样视觉拿不到的绝对参照:**

1. **绝对方向**:静止时读数是重力 9.80665 m/s²。物理常数,直接给出「哪边是下」。
2. **绝对尺度**:加速度是真实的 m/s²,于是运动是**米制**的。

> 这正是单目视觉缺的东西:单目不是「算不准尺度」,是**没有任何绝对参照物**,尺度在数学上不可观。

## 3. 前置知识 B:VIO 是什么

VIO = **V**isual-**I**nertial **O**dometry。逻辑是让两个「都很烂但烂法相反」的模态互补:

| | 强项 | 弱项 | 频率 |
|---|---|---|---|
| 相机 | 相对几何精确、**长期不漂** | 快速旋转/模糊即失效、无尺度、刷新慢 | ~30 Hz |
| IMU | 高频、快速旋转跟得住、自带重力与尺度 | 积分**必漂** | 200–1000 Hz |

- 相机负责**长期不漂**(观测修正 IMU 的积分漂移);
- IMU 负责**短期平滑 + 尺度 + 重力方向**,并填满相机帧间盲区(快速甩手时视觉断裂,陀螺仪仍在测)。

**尺度可观的机制**:视觉给出「形状对、大小任意」的轨迹,IMU 给出米制加速度;两者在时间上对齐拟合,那个未知缩放因子就被解出来了(经典结果,见 VINS-Mono 一系)。

**重要:VIO 不是真值。** 消费级 VIO 典型漂移量级约为行程的 0.1%–1%(走 100 m 错 0.1–1 m)。它比单目 SLAM 好得多,但**仍会漂**,长距离仍需回环。

## 4. 前置知识 C:ToF 硬件是什么

ToF = **T**ime **o**f **F**light,飞行时间法。主动发射调制光(通常近红外 ~850/940 nm),测光往返时间,`d = c·t/2`。光速 3×10⁸ m/s,1 米往返仅 6.7 ns,所以不能直接计时,实际两种实现:

| 方式 | 原理 | 特点 |
|---|---|---|
| **iToF**(间接) | 连续波调制 + 测发射光与回光的**相位差**:`d = c·Δφ/(4πf_mod)`,f_mod 典型 100–200 MHz | 手机 ToF 传感器最常见;相位周期性 → **距离模糊**(f_mod=100 MHz 时无模糊量程仅 ~1.5 m),需多频解模糊 |
| **dToF**(直接) | SPAD(单光子雪崩二极管)+ TDC 直接测光子飞行时间 | 精度可达 cm 级,成本/功耗高;iPhone LiDAR 属此类 |

**ToF 与单目/双目的本质区别:**

1. **主动**:自己打光,不依赖环境纹理 → 白墙、暗光也能测(但受阳光红外干扰)。
2. **一次观测即得绝对深度**:不需要基线、不需要运动、不需要第二帧。单目是被动三角化,**必须有视差**。
3. **米制绝对尺度**,直接是物理距离。
4. 代价:分辨率低(数千至数万点,远低于相机像素)、噪声大(多路径/反射率/阳光)、量程有限(手机通常 0.2–5 m)。

**与本文的关系(关键):**
`docs/plan.md` §1 的永久决策是「**永久单目 RGB,不加深度传感器**」,并据此排除了全部 RGB-D 方法(RTG-SLAM / SplaTAM / LoopSplat)。
**ToF 正是深度传感器最典型的形态**——所以排除 RGB-D 与该决策是自洽的。
而 **ARCore VIO 不引入任何新硬件**(IMU 是手机标配),因此**不违反**该决策。

> 顺带说明为什么 RGB-D SLAM 普遍比单目 SLAM 稳:它们的深度是**可观**的,不存在 §1 第 2 条的规范自由度。排除它们不是技术判断,是硬件约束。

## 5. ARCore 能提供什么

ARCore 是 Google 的 Android AR SDK,内部跑的就是一套 VIO(视觉 + IMU 紧耦合)。对外可取的量:

| 量 | API | 说明 |
|---|---|---|
| 位姿 | `frame.getCamera().getPose()` | 米制平移 + 四元数姿态,世界坐标系 |
| 跟踪状态 | `getTrackingState()` | `TRACKING` / `PAUSED` / `STOPPED` |
| 逐帧内参 | `getImageIntrinsics()` | 焦距、主点、图像尺寸 |
| 时间戳 | `frame.getTimestamp()` | 纳秒,与 `SensorManager` 传感器事件同一时基 |
| 图像 | `acquireCameraImage()` / `getTexture()` | CPU 图像 / GPU OES 纹理 |
| 深度(可选) | Depth API | 见下 |

**坐标系语义:**
- **米制**;Y 轴大致对齐重力(因为知道哪边是下);原点是会话开始位置。
- 不是「绝对世界坐标」,但**是真实米**。长距离仍会漂(§3)。

**三个必须注意的坑:**

1. **内参必须用 ARCore 给的,不能用 `CameraCharacteristics` 读的。**
   ARCore 的图像流可能被裁切/缩放过,它的内参是**针对它自己那一路图像**的。
   → 走这条路时,`docs/android_camera_intrinsics.md` 与 `scripts/android_intrinsics.py` 那一整套换算**不再需要**。
2. **内参要跟图像来源配对。** CPU 图像用 `getImageIntrinsics()`,GPU 纹理用 `getTextureIntrinsics()`,且纹理通常还需 `getTextureTransform()` 校正显示旋转。**用错配的内参会静默地毁掉重建。**
3. **可用分辨率需实测确认。** ARCore 不一定提供 1080p;要经 `CameraConfig` 筛选。当前 720p 的目标能否满足,**未验证**。

**两个有用的附带能力:**

- **Recording & Playback API**:可把一次会话(相机帧 + IMU + 位姿)录成 MP4,之后**确定性重放**。重放本身仍需在设备上跑一个 app 把位姿 dump 成文件,但**只需写一次,之后完全离线**在 4090 上反复调算法。对「不想每次都举着手机走一圈」的场景是纯赚。
- **Depth API**:在很多设备上**不需要 ToF 硬件**,是用连续帧 + VIO 位姿做 depth-from-motion 算出来的(有 ToF 的设备才用 ToF)。**同样不违反「不加深度传感器」的决策**,可提供一份带米制尺度的稠密深度先验 —— 正好对应「注入先验把欠定问题变超定」的思路。
  注意:它本质仍是被动方法,精度与视差挂钩。**是否可用、精度如何,未验证。**

**额外前提:** 设备需在 ARCore 支持列表内,且安装 Google Play Services for AR。

## 6. 提案:具体设计

### 6.1 核心变化:联合估计 → 条件估计

```
【现状】图像 → ORB-SLAM3(位姿 + 稀疏地图,共享观测) → mapper(位姿 + 几何联合优化) → splat

【提案】ARCore(位姿 + 内参 + 时间戳 + 图像) → 云端
                                            → mapper(位姿固定,只解几何/外观) → splat
```

问题从 **joint estimation** 降级为 **conditional estimation**。这是本提案的全部实质。
用「注入先验」的语言说:ARCore 提供了一个极强的先验(米制位姿),把优化问题的条件数改好了。

### 6.2 手机端:导出什么

每帧一条记录,与图像严格对应:

| 字段 | 含义 | 备注 |
|---|---|---|
| `timestamp_ns` | ARCore 帧时间戳 | 纳秒,用于配对图像与位姿 |
| `image` | 该帧图像 | 与位姿**必须来自同一帧** |
| `pose` | 4×4 或 (t, q) | ARCore 世界坐标系,米制 |
| `intrinsics` | fx, fy, cx, cy, w, h | **该路图像自己的**内参 |
| `tracking_state` | TRACKING/PAUSED/STOPPED | 必须传,见 §6.4 |

**位姿坐标系转换(容易踩,先写清楚):**
ARCore 相机是 OpenGL 约定(x 右、y 上、**z 向后**,看向 -Z);COLMAP/OpenCV/3DGS 是(x 右、y 下、**z 向前**)。
两者只差绕 X 轴 180°:

```
R_wc_cv = R_wc_arcore · diag(1, -1, -1)
```

**内参缩放**:若为省带宽把图像下采样后再上行,**内参必须同比缩放**,否则尺度全错。

### 6.3 云端侧:固定位姿的 3DGS 训练器

这里有一个架构上的重要推论:

> **Photo-SLAM 里 ORB-SLAM3 存在的唯一职责就是「自己算位姿」。位姿外来了,这个组件就没有职责了。**

于是链路可以大幅简化:

- **删掉**:ORB-SLAM3 及其依赖链(Pangolin / DBoW2 / g2o / Sophus / 词袋文件)、`libORB_SLAM3.so`、位姿 BA。
- **保留**:高斯表示 + CUDA 光栅化器 + mapper 的训练循环(但改为**位姿固定**)。
- **替代**:一个接受给定位姿的 3DGS 训练器(原版 3DGS / gsplat 这类吃 COLMAP 格式位姿的实现即可)。

附带好处:`docs/m2_photoslam_handoff.md` §3 记录的那一整串 C++ 编译地狱(torch ABI、boost 序列化 ABI、CUDA OpenCV、cxx11-abi LibTorch……)**大部分会消失**——因为那条依赖链本身就是 ORB-SLAM3 拖进来的。

### 6.4 与现有里程碑的关系

| 里程碑 | 受影响部分 | 说明 |
|---|---|---|
| M3.1 手机端 | **完全替换** | 放弃 IP Webcam,改为自研 ARCore app。这是本提案最大的一次性成本 |
| M3.4 相机配置 | **简化** | 内参由 ARCore 逐帧提供,不再需要自己标定/换算 |
| M3.5 喂给 Photo-SLAM | **替换** | 改为「喂给固定位姿训练器」;增量逻辑仍需自己写 |
| M4 增量传输 | 不变 | 协议与位姿来源无关 |
| M5 Web 端 | 不变 | — |

**注意:M3.2 的 SSH 反隧道、M3.3 的 ffmpeg 落盘会失去意义**(不再从 RTSP 拉流)。但若采用「手机本地落盘 + 事后上传」的采集方式,反隧道仍可用于取数据。

## 7. 预期收益(⚠️ 全部未验证)

| # | 预期收益 | 依据 | 置信度 |
|---|---|---|---|
| 1 | **尺度变为米制** | IMU 的重力/加速度提供绝对参照(§2) | 高(原理确定) |
| 2 | **位姿-几何解耦,消除「几何迁就位姿」** | 位姿不再是自由度(§6.1) | 高(原理确定) |
| 3 | **快速旋转不再丢跟踪** | 陀螺仪填帧间盲区(§3) | 中 |

| 5 | **链路与依赖大幅简化** | 可删掉 ORB-SLAM3 整条依赖(§6.3) | 中 |

> 关于第 6 条:原理上「消除位姿-几何耦合」应当直接改善拉丝/发软,但**改善幅度未经测量**。不要把它当成承诺。

## 8. 代价与风险

| # | 代价/风险 | 严重度 | 说明 |
|---|---|---|---|
| 1 | **必须改用 ARCore 自己的相机流** | **高** | 位姿是对着 ARCore 那一帧算的;继续用 IP Webcam 的流会导致位姿-图像错配。→ **放弃 IP Webcam,写原生 app**。这是最大的一次性成本,`docs/plan.md` M3.1「由简到繁」的路线到此必须换挡 |
| 2 | 内参必须跟 ARCore、跟图像来源配对 | 中 | §5 坑 2,错配会静默毁掉重建 |
| 3 | 可用分辨率可能不足 | 中 | ARCore 不保证给到 720p,**需实测** |
| 4 | **跟踪丢失会毁掉地图** | 中 | 返回 PAUSED/STOPPED 时位姿会跳。mapper 必须处理:暂停建图 / 等恢复 / 该段插值。若把 PAUSED 段的位姿当真用,会污染全局几何 |
| 5 | VIO 仍会漂 | 中 | §3。长距离仍需回环;「无漂移」是误解 |
| 6 | 闭源黑盒 | 中 | 前端不可调、内部状态不可见,出问题只能猜 |
| 7 | 弱纹理/暗光失效 | 中 | 视觉那一半仍是特征法,与 ORB-SLAM3 同样的失效模式 |
| 8 | 设备兼容性 | 低 | 需在 ARCore 支持列表 + 安装 Google Play Services for AR |
| 9 | Rolling shutter 未解决 | 低 | ARCore 不校正卷帘;位姿是逐帧时间戳的,帧内畸变仍在 |
| 10 | 学习/调试成本 | 中 | 新增 Android 原生 app 开发 |

## 9. 与已锁定决策的关系(逐条对照 `docs/plan.md` §1)

| 永久决策 | 本提案是否冲突 | 说明 |
|---|---|---|
| 深度:**永久单目 RGB,不加深度传感器** | **不冲突** | IMU 是手机标配,非新增硬件。ARCore Depth API 亦为软件计算(§5) |
| RGB-D 类方法(RTG-SLAM/SplaTAM/LoopSplat)排除 | **不冲突** | 本提案不引入真实深度输入;可选深度先验走软件路径且是可选项 |
| 计算:云端 RTX 4090 | **不冲突** | 计算仍在云端;手机端只多了一个采集 app |
| 延迟:端到端 ≤3s(目标 1–2s) | **有利** | 省掉 BA,预期延迟下降 |
| 场景:室内 + 室外 | **部分有利** | 户外强光/弱纹理可能反而更差,需实测 |
| 展示端:仅 PC 浏览器 | **不冲突** | 不变 |
| **推流:IP Webcam(RTSP)起步** | **冲突** | 这条需改为原生 ARCore app。若采纳,应在 `plan.md` §3 显式标注 |

> 唯一需要修改 `plan.md` 的地方是「推流方式」那一行,且**仅在正式采纳时才改**。

## 10. 如果要采纳,最小验证路径(spike)

目标:**在写完整 app 之前,先判断收益是否真实存在。** 建议顺序:

1. **先录数据集,不写实时链路。** 写一个最小的 ARCore app,遍历若干帧,把 `(图像 JPEG + pose + intrinsics + timestamp + tracking_state)` 落盘成文件(或直接把 ARCore 的 Recording 重放一遍 dump 出位姿)。
   → 只需一次手机操作,之后完全离线。
2. **上云:帧 + 位姿 → 固定位姿 3DGS 训练器**(COLMAP 格式即可,注意 §6.2 的坐标系转换)。
3. **对照组:同一段素材走现有 Photo-SLAM 链路**(`scripts/run_photoslam.sh`)。
4. **对比维度**:几何是否更「实」(拉丝/发软是否改善)、尺度是否为真实米、跟踪是否更稳、耗时对比。
5. **判定**:若第 4 步无显著改善,则本提案的收益假设不成立,应停止,不必投入原生 app 开发。

> 路径 1 的另一种更省事的形态:用 ARCore **Recording & Playback** 先录再重放 dump,免去实时链路的调试。

## 12. 术语表

| 术语 | 含义 |
|---|---|
| IMU | 惯性测量单元;陀螺仪 + 加速度计 |
| VIO | 视觉惯性里程计;视觉 + IMU 紧耦合估计位姿 |
| ToF | 飞行时间法测距;主动发射调制光测往返时间 |
| iToF / dToF | 间接(相位差)/ 直接(SPAD 计时)飞行时间 |
| 规范自由度 | gauge freedom;此处指单目尺度在数学上不可观,而非算法不准 |
| 联合估计 / 条件估计 | joint estimation(位姿与几何一起解)/ conditional(位姿给定,只解几何) |
| 摊销推断 | amortized inference;把 per-scene 优化换成训练时学到的先验,一次前向出结果 |
| shape-radiance ambiguity | 错误几何 + 视角相关外观也能解释同一组 2D 观测,导致几何欠定 |
